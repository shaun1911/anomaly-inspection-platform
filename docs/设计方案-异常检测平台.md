# 工业异常检测平台 · 设计方案

> 状态：**待评审**（只做方案，不含实现代码）
> 依据：三轮答复（纯内网、2K JPEG <300KB、异步、现场可反馈误判、复核 10 min/天、默认指标、二期大屏优先、多模型 + 配置单）

## 0. 一页摘要

**要建什么**：纯内网的一台 GPU 服务。现场设备通过 HTTP 异步推图（2K JPEG），服务返回 OK/NG + 分数 + 缺陷区域；结果与图片入库；系统按分数分层抽样、接收现场误判反馈，自动攒出下一轮训练数据并自动训练出候选模型，人在页面上点「发布」后热切换，可一键回滚。

**不建什么**：不做边缘盒子、多租户 SaaS、视频流时序检测、掩膜标注（二期）、完整大屏（二期首项）。**一句话验收**：一条线，从「传数据」到「新模型自动训练 + 人工发布生效」全程页面操作；现场能异步拿结果、能上报误判。

**关键数字**（本机 RTX 5080 实测，5090 约 2×）：

| 环节 | 实测/估算 |
|---|---|
| 单图推理（wrn50, 256px） | 6.2 ms（batch=1）/ 1.9 ms（batch=8） |
| 2K JPEG 解码（降采样 1/4） | 8~15 ms |
| PatchCore 训练（40 张） | 11 s；500 张约 3~5 min |
| 异步端到端（上传→可查询结果） | p95 ≤ 3 s |

## 2. 范围

### 2.1 范围内（演示档）

1. **异步推理与现场反馈**：`POST /infer` → 202 + `job_id`（请求带产品编码，结果轮询/回调，批处理与超时降级）；`POST /infer/feedback` 上报「误判/漏检」进样本池。
2. **数据管理**：建数据集、上传正常品/缺陷图、缩略图、按 hash 去重。
3. **训练与发布**：页面发起 → 队列执行（按模型排队、可手动排序）→ 模型版本 + 指标 + 日志；候选对比 → 人工发布 → 热切换 → 一键回滚，作用域为单个模型。
4. **数据飞轮**：分层抽样（含现场反馈）→ 高置信自动入库 / 低置信人工确认 → 自动训练 → 候选评估。
5. **多模型与新建模型**：产品编码 → 模型绑定、配置单一键加载、常驻池与 LRU 兜底；五步向导、产品冲突拦截、按数据量给推荐值。
6. **最小可观测**：健康检查、任务进度、每日调用量/NG 率/过杀率/延迟（`/api/stats/daily`，即二期大屏的数据底座）。

### 2.2 范围外（明确不做）
| 不做 | 原因 | 何时 |
|---|---|---|
| 统计大屏（可视化编排、多维度下钻、大屏轮播） | 二期第一优先，演示档只做数据接口 + 极简页面 | 二期首项 |
| 掩膜标注工具 | 无掩膜数据；成本高 | 二期 |
| 多产线 / 细粒度 RBAC | 单线试点，先「一线一 token + 一个管理员」 | 三期 |
| 批量恢复、按产品灰度发布 | 归档包 + manifest 手工恢复已够用 | 二期 |
| 视频流 / 时序异常 | 场景是单张表面图 | 不适用 |
| TensorRT / 多卡 / 分布式 | 当前延迟已达标 | 有节拍压力时 |
| 边缘部署 | 已确认远程 | 不适用 |
| 缺陷测量 / 定级分类 | 只回答「是否异常 + 在哪」 | 二期可加 |

### 2.3 多模型与产品编码语义
| 项 | 结论 |
|---|---|
| 模型数量 | 一个服务同时提供多个模型（不是一个模型一个服务） |
| 路由键 | 请求传完整产品编码（如 `AB-1234-02`），按 `product.code` 精确匹配（trim + 转大写归一） |
| 绑定关系存放 | 数据库，不写进 bundle（同一模型可服务多个编码；写死会导致重构） |
| 绑定对象 | 绑「模型」这个实体，不绑版本 |
| 一对多 | 一个模型可绑 N 个产品编码；一个产品编码只能绑一个模型 |
| 换型通知 | 推图请求自带产品编码；另提供查询接口让现场确认目标模型已加载 |
| 预加载 | 需要；当班集合必须提前进显存（冷加载落在换型首件上不可接受） |
| 未知编码 | 直接返回 **422**，绝不 fallback 到默认模型（错判比不判更危险） |
| 已停用编码 | 返回 **410 Gone**，提示使用新编码 |

编码是**不透明字符串**，族/零件/序号只是可选展示字段，不参与路由。`product.code` **创建后不可修改**——已打印的标签、工单、纸质流转卡都印着编码，改码等于现场标签全部失效；要换编码 = **停用旧码 + 新建新码**，旧码保留映射历史（查询时仍能回答「当时这个码用的哪个模型」），旧码 → 新码的迁移映射（`product_alias`）放二期。产品路由页展示「编码 / 描述 / 绑定模型 / 生效版本 / 加载状态」，并提供「新增编码」（把新助记符绑到已有模型，这是最常见的日常操作）。

## 4. 架构

### 4.1 拓扑（纯内网，双进程）
```
 现场设备/工控机 ──HTTP(内网)──► 反向代理（TLS 终止、限流、体积上限）
                                    │
                     ┌──────────────▼───────────────┐
                     │ AIP-Web（uvicorn，单进程）   │
                     │  /infer  异步推理 + 批队列   │
                     │  /api    业务 + 页面(SSR)    │
                     └──────┬──────────────┬────────┘
                            │              │
                   ┌────────▼──────┐  ┌────▼──────────┐
                   │ AIP-Worker    │  │ 常驻模型池    │
                   │ 独立进程，串行 │  │ 多 bundle 驻  │
                   │ 执行训练队列   │  │ 显存 + LRU    │
                   └────────┬──────┘  └────┬──────────┘
                            └──────┬───────┘
                     盘：artifacts / data / db / logs
```

### 4.2 选型与理由
| 层 | 选择 | 理由 |
|---|---|---|
| 推理内核 | 复用 `aip` runtime（ONNX/torch 双后端 + 批推理） | 已验证：wrn50 b8 = 258 img/s；双后端分数差 <1e-3 |
| 图像解码 | OpenCV `IMREAD_REDUCED_COLOR_4/2` | 2K→目标尺寸直接降采样解码，比「全解码再 resize」快 2~3 倍 |
| 模型分发 | bundle（metadata + onnx + ckpt） | 自包含、可回滚、可拷走 |
| 训练 | anomalib `Engine` + PatchCore(wrn50) | 复用 35 个模型与评测体系 |
| Web | FastAPI + Jinja2 + **本地化 HTMX** | 纯内网不能用 CDN；不引 React 构建链，省 1~2 周 |
| DB | SQLite(WAL)，预留 PostgreSQL | 每天万级写入、单进程；零运维 |
| 队列 | 全局唯一队列 + 单 worker | 只有一块 GPU，只允许一个训练任务 |
| 代理 | Caddy + 内部 CA；Windows 上可用 nginx/IIS（`AIP-Proxy`，可选） | 自动签发内网证书，浏览器/设备信任一次 |
| 模型权重 | 离线放入 `C:\AIP\weights`（`TIMM_HOME` 指向它） | 纯内网无法下载；否则训练直接失败 |
| 服务形态 | 原生 Windows 服务（NSSM）：`AIP-Web` + `AIP-Worker` | 无虚拟化层，GPU 直通；训练 OOM 不带走在推理 |

### 5.2 模型 / 版本 / 绑定 三层分离
```
product (产品编码)  ──绑定──►  model (模型实体)  ──1:N──►  model_version (版本，各自成线)
AB-1234-02                    M-BR-01（支架右件·表面）        v1 → v2 → v3 → v4
```

由此得到三个好处：**发布不改绑定**（M-BR-01 发 v4，所有绑它的编码自动切到 v4，无需逐条改绑定）；**回滚隔离**（只影响该模型的版本线，其它模型纹丝不动）；**训练按模型排队**（一个模型一个训练任务，队列串行执行，互不干扰）。

**训练队列语义**：任务属于某个 `model`，队列**全局唯一、串行执行**（同一时刻只有 1 个训练）；支持**手动排序**（上移/下移 = 优先级），默认按提交时间 FIFO；同一模型不允许两个任务同时在队列里（重复提交直接返回已有 job）；排队中的任务可取消，正在执行的只能「中止并丢弃」。

### 5.3 约束与保留要点

- **软删优先**：有历史引用的只能「停用/归档」，删除时必须说明被谁引用（「被 M-BR-01 绑定，无法删除」），而不是笼统的「不能删」。
- **编码与编码类字段不可改**（编码、数据集 ID、模型 ID）——外部已引用；所有 C/U/D 写审计：谁、何时、改了哪个字段、旧值 → 新值。
- 被引用进配置单的 `model_version` 必须处于 `active` 或 `candidate`（退役版本禁止绑入，防止误用）。
- 图片不进库，只存路径；原图按 OK/NG 分层保留（见「数据归档与清理」章），缩略图 + 元数据长期保留；`dataset.fingerprint` 保证「哪个模型是哪份数据训的」可查。

## 6. 关键流程

### 6.1 异步推理（主链路）
```
设备 ──POST /infer (multipart: line_id, token, product_code, image, idempotency_key)──►
  1. 令牌校验、体积/尺寸校验（>16MB → 413）；解析 product_code → 绑定模型（未知 422、停用 410）
  2. 落原图 → 建 inference_job(queued) → 立即返回 202 {job_id}
  3. worker：降采样解码 → 入批队列（≤8 张或 ≤8ms）→ 目标 bundle 推理
  4. 写 inference_result（含 decode_ms / latency_ms）→ job 状态 done
  5. 现场二选一取结果：GET /infer/{job_id}（轮询，默认，内网最稳）；或 callback_url（webhook，可选，需现场能接收入站）
```

**为什么异步**：2K 解码 + 排队 + 落盘会吃掉同步预算，异步把「设备超时」风险降到最低。**幂等**：`idempotency_key`（设备 ID + 图 sha256）24 h 内重复请求直接返回原 `job_id`。**保留同步接口** `/infer?sync=1`（调试与低延迟场景，≤800 ms 超时）。**失败语义**：`failed` + `error_code`，设备侧重试（幂等键保证不会重复计费/重复入库）。**响应回显 `model_version`**，保证每张图能追溯到「哪个模型判的」。

### 6.2 现场反馈（误判上报）
```
设备/工位系统 ──POST /infer/feedback {result_id, verdict, defect_type?, note?}──►
  1. 写 feedback（唯一约束：每个 result 一条，可覆盖）
  2. 同事务创建 pool_item(source=feedback, status=accepted)
  3. verdict=ng 且结果原判 OK → 记为「漏检」，进验收集（不能进训练集）
  4. verdict=ok 且结果原判 NG → 记为「过杀」，进训练集 normal
  5. 更新 daily_stat.feedback_rate
```

**这是本方案里最重要的一条闭环**：现场比复核员更早知道对错，且不需要额外人工时间；反馈样本优先级最高，且可直接触发一次训练（可配）。

### 6.3 建集与训练
```
建集：上传 zip/多选 → 选 label → 落 data/<model_id>/<日期>/ → sha256 去重 → 缩略图
     → 写 dataset_item；若数据集为空 → 自动切冻结验收集

训练：页面「训练」→ train_job 入队（归属模型）→ worker 串行执行：
  1. 导出 snapshot（train / frozen-val）
  2. Engine.fit(PatchCore(wrn50, coreset 0.1))
  3. 产出 bundle + metrics → model_version(candidate)
  4. 页面显示候选 vs active 指标对比（同一模型的版本线内比）
```

### 6.4 飞轮（每天一次，10 分钟人工预算）
```
每日 02:00（或池满 200，可配置）：
  1. 现场反馈样本全部并入（不占人工预算）
  2. 分层抽样，总量封顶 80 张
  3. 人工确认：40 张 × ~6 s ≈ 4 min（留 6 min 余量）
  4. 训练集 delta ≥ 50 → 自动训练
  5. 门槛：frozen-val 召回不降 且 过杀率不升 >2%（绝对）→ candidate 可发布
  6. 人点「发布」→ 热切换；异常 →「回滚」30 s 生效
```

### 6.5 换型与一键加载
```
操作工点「一键加载」
  1. 解析 codes → 产品 → 模型（去重）
  2. 容量预检：模型数 × 单模型显存 ≤ 可用显存？超了 → 提示并给出上限
  3. 并发预热（4）：逐项 pending → loading → ready / failed
  4. 全部 ready → 卡片变绿「已就绪，可开工」；有失败 → 标红并指出是哪个模型
  5. 记录 preset_load 事件（谁、何时、加载了几个、耗时）
```

- 换型前现场先调 `/routing/resolve?code=...` 确认目标模型已就绪；未就绪可先调 `/routing/preload` 等待，或直接推图（服务端同步加载，最多 2 s）。一个编码可出现在多张配置单里，加载时按模型去重（3 个产品共用 1 个模型只加载 1 次）。**配置单只影响预加载，不影响路由**：推图仍按 `product_code` 解析绑定，与当前加载了哪张配置单无关（避免「忘了切配置单就判错」）。
- **不做卸载**：已加载的模型保留（显存便宜），新配置单增量加载，超显存时按 LRU 淘汰不在任何已加载配置单里的模型。同一模型在一个班次内被重载 ≥3 次 → 告警「配置单漏配」；预热失败（bundle 损坏/显存不足）→ 该项标 `failed`，页面红色高亮，**不阻塞其余项**；启动时恢复上次加载的配置单，无则空闲。

## 7. 算法与质量

### 7.1 one-class 与阈值

正常品充足、缺陷少且无掩膜；PatchCore = 预训练特征 + 记忆库，只需正常分布，缺陷图用于评估与定阈值。阈值取「过杀率 ≤5% 时召回最高」的分数点，而非 F1 最优点；阈值随 bundle 固化，**按模型维护阈值表**，页面不提供全局滑杆（各模型最优阈值不同，一刀切会互相拖累），改动记审计。

### 7.2 冻结验收集（自动训练的前提）

每个模型独立一套：首次上传时抽 20% 正常 + 50% 缺陷图，`purpose=frozen`，指纹锁死；训练启动前校验指纹，变了就拒绝。只有「人工确认过」的样本进训练集，自动样本只能进 normal 或 pool；指标只在模型**自己的**冻结验收集上算，禁止跨模型平均。

### 7.3 抽样预算（按 10 min/天反推）
| 分层 | 条件 | 去向 | 每日上限 |
|---|---|---|---|
| feedback | 现场上报 | 直接入池（accepted） | 不设上限（人已看过） |
| low_conf | 0.35 ≤ score ≤ 0.65 | 人工确认队列 | **40** |
| high_conf_ok | score ≤ 0.2 | 训练集 normal | 20 |
| high_conf_ng | score ≥ 0.9 | pool(auto_ng)，仅作验收集 | 10（超出丢弃） |
| random | 全区间 | 审计/偏差监控 | 10 |

合计 ≤80 张/天，其中需人工的 ≤40 张（约 4~6 分钟），留出余量。配额**按模型分配**（`by_volume` 按昨日检测量比例，或 `even` 均分）并受全局上限约束，避免热点模型吃满配额、其它模型饿死；运行时间、总量、比例、各层上限与分数区间均可配置（见「抽样参数可配置化」章）。

### 7.4 指标与漂移
| 指标 | 定义 | 演示档目标 |
|---|---|---|
| 召回（主） | 缺陷判 NG 比例 | ≥ 0.95 |
| 过杀率 | 正常判 NG 比例 | ≤ 0.05 |
| 异步端到端 p95 | 上传→可查结果 | ≤ 3 s |
| 推理 p95 | worker 内 | ≤ 50 ms |
| 解码 p95 | 2K JPEG 降采样 | ≤ 20 ms |

线级 KPI（检测量/延迟）保留；模型级指标改为**模型健康度表**，逐模型展示，禁止跨模型求平均。漂移监控每日按模型计算 score 分布 PSI vs 该模型基线，>0.2 告警「分布漂移，建议重训」，并作为该模型自动训练触发依据（只告警该模型）。

## 9. 非功能

### 9.1 显存预算与常驻模型上限

GPU 竞争（单卡）：推理优先；训练限显存（`set_per_process_memory_fraction(0.6)`）+ 排夜间窗口；同一时刻仅一个训练任务；推理 p95 >100 ms 时训练暂停（可续跑）。冷加载实测（本机 RTX 5080，torch 2.10 cu130）：

| 指标 | resnet18 | wide_resnet50_2 |
|---|---|---|
| ONNX 冷加载 | 70 ms | 244 ms |
| torch 冷加载 | 174 ms（首个 1.9 s 含 CUDA 初始化） | 720 ms |
| 单模型显存（torch） | 25 MB | **129 MB** |
| 进程启动（import torch+anomalib） | 11.8 s（一次性） | — |

冷加载 0.2~0.9 s 正好落在换型首件上，所以**当班集合必须预加载**；显存极便宜（32 GB / 129 MB ≈ 200 个 wrn50 模型），实际一族产品 5~30 个，全量常驻也才 4 GB。策略是「**配置单驱动预热 + LRU 兜底**」：正常走预热，未命中时同步加载（single-flight，最多等 2 s）并告警。

| 场景 | 常驻模型数 | 显存（wrn50，129 MB/个） | 结论 |
|---|---|---|---|
| 单线单班 | 5~15 | 0.6~2 GB | 轻松 |
| 单线全产品族 | 30~50 | 4~6.5 GB | 可行 |
| 多线（二期） | 100+ | 13~26 GB | 接近上限，需要按线分组 + 共享主干 |

实测（RTX 5080，torch 后端，wrn50，训练集 40 张）：

| 项 | 数值 |
|---|---|
| 主干权重 | 119 MB |
| 记忆库（4096 patch × 1536 dim） | 25 MB |
| **单模型显存增量（实测）** | **122 MB** |
| 单模型 CPU 侧（进程内对象） | ~20 MB |

记忆库随训练集线性增长：`记忆库 ≈ 训练张数 × 1024 patch × 0.1(coreset) × 1536 dim × 4 B`。

| 训练集规模 | 单模型显存 | 32 GB 理论上限* | 5080 16 GB |
|---|---|---|---|
| 40 张 | ~122 MB | ~239 | ~106 |
| 200 张 | ~200 MB | ~146 | ~64 |
| 500 张 | ~434 MB | **~67** | ~30 |
| 1000 张 | ~800 MB | ~36 | ~16 |

\* 32 GB 折算 29 GB 可用（预留 3 GB 给 CUDA 上下文、批推理激活、显存碎片）。

**结论**：建议运行上限 **24 个模型**（当班配置单通常 5~15 个，留 3 倍余量给换型与 LRU 波动）；硬上限由「可用显存 ÷ 单模型显存」动态算，超过就 LRU 淘汰**不在当班配置单**的模型；若单线训练集普遍 >500 张，把常驻上限降到 16，并考虑「按产品族分组、组间共享主干」的二期优化。

### 9.2 存储与带宽（按 F3：300 KB/张）
| 项 | 估算 |
|---|---|
| 每线每天 3000 张 × 0.3 MB | **0.9 GB/天** |
| 原图保留 30 天 | ≈ 27 GB |
| 缩略图 + 数据库 + 日志 | < 5 GB/月 |
| 模型 bundle（wrn50 onnx ~120 MB × 10 版） | 1.2 GB |
| **建议盘** | **≥ 512 GB SSD**（含备份与缓冲） |
| 带宽 | 平均 0.09 Mbps，峰值按 10× ≈ 1 Mbps |

结论：存储与带宽不再是瓶颈，**瓶颈是 CPU 解码与人工复核**。

### 9.3 安全与可观测

一线一 token（哈希存储、可轮换）；管理口令 + 会话 Cookie（HttpOnly）；TLS 走内部 CA 签发，设备/浏览器信任证书一次，不依赖公网 CA；上传上限 16 MB、每线 20 rps 限流；原图保留期可配，删除任务每日执行；演示档不做 SSO/MFA，但 `audit_log` 先落表。请求 ID 贯穿（设备→job→result），每日汇总，告警项为连续 5 分钟 5xx、p95 超阈、训练失败、磁盘 >85%，告警带 `model_id` 并可按模型配置静默期。

## 10. 部署（Windows 11 Pro 原生服务）

### 10.1 为什么是原生服务
| 方案 | 可行性 | 代价 |
|---|---|---|
| **原生 Windows 服务（NSSM/sc.exe）** | ✅ 推荐 | 无虚拟化层，GPU 直通，`torch 2.10+cu130` 在 Windows 上已验证可用（本机就是） |
| Docker Desktop + WSL2 | 能跑，但不建议产线用 | 商用许可要订阅；WSL2 里的 CUDA 依赖 Windows 驱动 + WSL 内库的版本匹配；Docker Desktop 自身要常驻托盘进程、会自更新；服务开机自启要额外配置 |
| Podman / WSL 裸装 | 不建议 | GPU 支持不成熟 |

结论：Windows 上把「进程 + 服务 + 脚本」做扎实，比套一层容器更可靠、更好排查。

### 10.2 目录与服务拓扑
```
C:\AIP\
  python\      Python 3.12 + venv          app\    代码（aip 包）
  wheelhouse\  离线轮子（torch cu130 + 依赖，约 3.5 GB）
  data\        原图、缩略图（按 产品/日期 分层）
  artifacts\   模型 bundle（每个模型一个目录 + current 指针）
  db\          SQLite（WAL）               logs\   轮转日志
  config\.env  令牌、保留天数、显存上限、存放路径
  tools\nssm.exe 服务管理器                备份\   每日备份落点（另一个盘）
```

| 服务 | 进程 | 职责 | 端口 |
|---|---|---|---|
| `AIP-Web` | uvicorn | 推理 API + 页面 + 业务接口 | 8000 |
| `AIP-Worker` | python worker | 训练队列执行（独立进程，独占训练显存） | — |
| `AIP-Proxy`（可选） | nginx/IIS | TLS 终止 + 反向代理 | 443 |

**为什么要拆成两个进程**：训练会吃满显存、可能崩；跑在同一个进程里，一次训练 OOM 就把在线推理带走了。拆开后 Worker 崩了只影响排队任务。

### 10.3 离线安装包与安装步骤

安装包 = 一个约 **5 GB** 的目录，用 U 盘/移动硬盘拷到 `C:\` 解压：

| 子目录 | 内容 | 体积 |
|---|---|---|
| `installer\` | `python-3.12.x-amd64.exe`、`nssm.exe`、VC++ 运行库（`vc_redist.x64.exe`） | ~120 MB |
| `wheelhouse\` | torch 2.10.0+cu130、torchvision 0.25.0+cu130、anomalib 及其依赖（lightning/torchmetrics/timm/kornia/opencv-headless…） | ~3.5 GB |
| `weights\` | timm 主干（`resnet18.a1_in1k`、`wide_resnet50_2.racm_in1k`），预先放好，`TIMM_HOME` 指过去 | ~300 MB |
| `app\` | `aip` 包 + 前端静态资源 + `requirements.txt` | ~2 MB |
| `deploy\` | `install.ps1`、`install-service.ps1`、`healthcheck.ps1`、`backup.ps1`、服务配置模板 | <1 MB |
| `docs\` | 部署手册（图文）、验收清单、故障排查 | ~5 MB |

**安装步骤（目标：≤30 分钟）**：① 装 Python 3.12（勾选 Add to PATH）、VC++ 运行库；② `python -m venv C:\AIP\python` 并按 `pip install --no-index --find-links C:\AIP\wheelhouse -r requirements.txt`；③ 拷贝 `app`、`artifacts`（首次为空）、`weights`，写 `config\.env`（token、路径、显存上限）；④ `install-service.ps1` 注册 `AIP-Web` 与 `AIP-Worker`（NSSM），设置失败重启与日志路径；⑤ `healthcheck.ps1` 注册任务计划（每 2 分钟）；⑥ 冒烟：`/health` → 推一张图 → 建一个最小数据集跑一次训练，确认无外网依赖（可用防火墙封 80/443 验证）。

**驱动是不可打包的前提**：服务器需预装支持 CUDA 13 的 NVIDIA 驱动（≥580）。安装包只校验 `nvidia-smi` 与 `torch.cuda.is_available()`，不负责装驱动。Python 推荐 **3.12**（wheel 覆盖最全，anomalib 生态验证最多）；3.13 也可用（本机开发环境就是 3.13，跑通了），但个别包（如 `imagecodecs`）依赖 abi3 轮子，出问题排查成本高；一旦选定，**开发机与服务器必须同版本**，否则 wheelhouse 白做。

### 10.4 Windows 11 Pro 的设置与坑（不设会出事）
| # | 项 | 命令 / 位置 | 不做的后果 |
|---|---|---|---|
| 1 | 关闭睡眠/休眠、快速启动 | `powercfg /change standby-timeout-ac 0`；`powercfg /h off` | 机器睡着 → 产线推图全部超时；关机后 GPU 状态异常，服务起不来 |
| 2 | 延迟自动更新 | 设置 → Windows 更新 → 高级 → 活动时间设满（Pro 可用组策略强制） | 夜里重启打断训练；训练任务需检查点 |
| 3 | Defender 排除目录 | `Add-MpPreference -ExclusionPath C:\AIP`（对 `data`、`artifacts`、`db`，需管理员） | 模型加载慢 2~5 倍、SQLite 锁冲突 |
| 4 | 长路径 | `LongPathsEnabled=1`（注册表/组策略） | 路径 >260 字符时深层数据目录报错 |
| 5 | 时间同步 | `w32time` 指向内网 NTP | 队列/审计时间错乱 |
| 6 | 关闭开机自启的无关软件 | 任务管理器 → 启动 | 显存被浏览器/游戏中心占用 |
| 7 | 显示器可拔 | 无需外接显示器（服务会话无头运行） | 首次部署时需实测一次 GPU 是否正常 |

此外四个必须知道的坑：**控制台 GBK**——Rich 进度条打 emoji 直接 `UnicodeEncodeError` 崩训练，对策是 `PYTHONUTF8=1` + 启动时 `sys.stdout.reconfigure(utf-8)`，日志文件强制 UTF-8（本机已踩过）；**SQLite `database is locked`**（杀软/备份占用）——WAL + `busy_timeout=5000` + 备份用 `.backup` 而非直接拷文件；**服务账户权限**（GPU 访问、目录写权限）——用 `LocalSystem` 或专用账户并授予「作为服务登录」，目录 ACL 只给该账户；**多进程 spawn**——训练 worker 用独立进程（不是 multiprocessing），DataLoader `num_workers=0`（Windows 上 spawn 开销大且易卡）。

### 10.5 服务、自愈、备份与升级

- 用 **NSSM**（免费、单 exe）把进程注册成服务：`AppDirectory`、`AppStdout`、`AppStderr`、`AppExit` 默认重启。系统自带 `sc.exe` 也能注册，但**不处理 stdout 重定向与优雅退出**，Windows 上容易留僵尸端口占用；NSSM 更省事，若不允许第三方工具，退化为 `sc.exe` + 应用内日志。**看门狗**：任务计划每 2 分钟跑 `healthcheck.ps1`，连续 3 次 `/health` 失败 → `Restart-Service AIP-Web`；**开机自启**：服务 `start=auto`，Windows Update 重启后能自己起来。
- **备份**：任务计划每日 02:30 跑 `backup.ps1`：`sqlite3 .backup` + `robocopy /MIR artifacts` + 原图按保留期清理，保留 14 天。**升级**：停服务 → 替换 `app/` → `pip install -r` → 起服务（中断 <30 s），模型升级走页面发布，不重启进程（热切换）；**回滚**：代码回滚到上一个目录副本，模型回滚走页面按钮。
- **可移植性**：服务端是纯 Python，将来若要搬 Linux，换掉服务注册与路径配置即可，业务代码不动。

## 14. 多模型复盘：被「单模型假设」污染的地方

下面的 15 处设计是按「一条线一个模型」写的，引入多模型后**全部要改**，否则会出现「一个模型的动作干扰另一个模型」的隐性错误。

| # | 位置 | 原设计（单模型假设） | 多模型下的问题 | 新设计 |
|---|---|---|---|---|
| 1 | 概览 KPI | 一个「当前模型」+ 一套召回/过杀 | 无法用单一指标代表 4 个模型 | 线级 KPI（检测量/延迟）保留；模型级指标改为**模型健康度表**，逐模型展示 |
| 2 | 发布 | 全局一个 active | 发布一个模型影响多个产品 | 按模型发布；**冒烟集逐产品验证**后才允许 |
| 3 | 回滚 | 全局回滚 | 回滚会把别的模型也带走 | 按模型回滚，只动该模型的版本线 |
| 4 | 阈值 / 灵敏度 | 一个全局滑杆 | 每个模型的最优阈值不同 | **按模型的阈值表**；页面不提供全局滑杆（避免一刀切） |
| 5 | 数据集 | 一条线一个数据集 | 不同模型的数据混在一起会互相污染 | 每模型一个数据集 + 独立冻结验收集 |
| 6 | 训练队列 | 「一次训练一个模型」但展示是全局 | 指标/日志无法区分归属 | 队列按模型、指标按模型；同一模型禁止重复排队 |
| 7 | 指标口径 | image_AUROC 一条线一个 | 跨模型求平均没有意义 | 每模型只在**自己的**冻结验收集上算；禁止跨模型平均 |
| 8 | 抽样配额 | 全局 80 张/天 | 热点模型吃满配额，其它模型饿死 | **按模型配额** + 全局上限；配额按该模型昨日检测量比例分配 |
| 9 | 复核队列 | 只显示分数 | 不知道是哪个模型/产品的样本 | 每条带「产品 → 模型 → 版本」，确认后进对应模型的数据集 |
| 10 | 自动训练触发 | 全局池满 N 张 | 一个模型的数据增长触发全部重训 | 每模型独立阈值；只重训有变化的模型 |
| 11 | 漂移监控 | 全局 PSI | 掩盖单个模型的漂移 | 按模型 PSI；某模型超阈值只告警该模型 |
| 12 | 启动 / 预热 | 启动加载「当前模型」 | 多模型时不知道该加载谁 | 启动恢复**上次加载的配置单**；无则空闲 |
| 13 | 存储布局 | `data/<日期>/` | 无法按模型清理/迁移 | `data/<model_id>/<日期>/`；删除某模型时可整目录回收 |
| 14 | 告警 | 全局一条告警通道 | 无法定位是哪个模型出了问题 | 告警带 model_id；按模型配置静默期 |
| 15 | API 契约 | `/api/train`、`/api/stats` 无模型维度 | 调用方无法指定/过滤 | 全部加 `model_id`；`/api/stats?group_by=model` |

**三条原则**，用来判断以后新增功能是否又一次踩进单模型假设：① 任何「全局唯一」的配置，都要问一句它该不该按模型拆（阈值、灵敏度、数据集、验收集、配额）；② 任何「聚合指标」都要能下钻到模型，否则无法归因；③ 任何「发布/回滚/删除」动作，必须明确作用域是模型还是产线（默认模型，产线级需二次确认）。

## 15. 新建模型向导

### 15.1 先分清两件事
| 动作 | 含义 | 结果 |
|---|---|---|
| **新建模型** | 新的检测任务（新产品/新工位/新缺陷类型） | 一个 `model` 实体，绑定产品编码，无版本 |
| **训练** | 给已有模型产出新版本 | 该模型 `v(N+1)`，状态 candidate |

向导只负责前者；训练走训练队列。**一条硬规则：一个产品只能绑一个模型**——`model_binding.product_id` 唯一，因为推图按 `product_code` 解析模型，一个产品绑两个模型就无法确定用谁。因此向导第 2 步必须**拦截冲突**：已被其它模型占用的产品显示为灰、标注占用者，不能选；已选中但被并发占用的，提交时报 409。

### 15.2 五步向导
```
① 基本信息  名称 / 检测对象 / 负责人          （可选：从现有模型复制配置）
② 绑定产品  勾选产品编码                      ← 冲突拦截
③ 训练数据  新建或复用数据集；上传正常品/缺陷图  ← 数量与质量校验
④ 训练配置  主干 / 输入尺寸 / coreset / 阈值策略  ← 按数据量给推荐值
⑤ 确认创建  摘要 + 预估显存与训练时长 + 冒烟集     → 创建
```

| 步骤 | 阻塞项 | 警告项（可继续） |
|---|---|---|
| ① | 名称为空；重名 | 名称过长 |
| ② | 未选产品；所选产品已被占用（409） | 所选产品跨了 3 个以上零件（可能建错模型） |
| ③ | 无正常品；图片格式不支持 | 正常品 < 50 张（召回不稳）；无缺陷图（只能评估图像级，pixel-F1 不可信）；尺寸不一致（将统一 resize） |
| ④ | 输入尺寸与产品实际分辨率偏差 >2 倍 | coreset 过高导致显存超限（按估算提示） |
| ⑤ | 冒烟集未准备（可选择「跳过并承担风险」） | 预估训练时长 > 30 分钟（建议先小样本试训） |

推荐值逻辑（第 ④ 步）：

| 输入 | 推荐 |
|---|---|
| 正常品 < 100 张 | `resnet18` + 输入 256 + coreset 0.1（快，先验证可行性） |
| 100~500 张 | `wide_resnet50_2` + 输入 256 + coreset 0.1 |
| > 500 张或缺陷极细 | `wide_resnet50_2` + 输入 384 + coreset 0.05（显存换精度） |
| 阈值策略 | 默认「召回优先」（漏检代价高）；可选「均衡」 |

第 ② 步按「已绑 N 个编码」分组展示，强调多对一，行内显示占用模型。

### 15.3 创建后发生什么

写 `model`（status=active，无版本）→ 绑定所选产品编码（事务内，冲突回滚）→ 建数据集（或关联已有）+ 初始化冻结验收集（按比例抽，指纹落库）→ 可选「创建后立即训练」（往队列插一个任务）→ 跳转到模型详情，提示「还差一次训练才能上线」。模型在没有版本时，列表显示「未训练」，不可发布、不可绑定配置单。

| **训练任务** | 入队 | 队列 / 历史 | 排序 / 取消（排队中） | 删除已完成记录 | ✅ |

| 检测记录 | 推图产生 | 查询 / 统计 | — | 按策略清理 | 仅自动 |

**三条统一规则**：① **软删优先**——有历史引用的只能「停用/归档」，不能物理删，删除时**必须说明被谁引用**（「被 M-BR-01 绑定，无法删除」），而不是笼统的「不能删」；② **编码与编码类字段不可改**（编码、数据集 ID、模型 ID），外部已引用；③ **所有 C/U/D 写审计**：谁、何时、改了哪个字段、旧值 → 新值。

**为什么有些操作故意不给**：删除已发布过的版本——产线可能还在用，删了无法追溯「这批货是谁判的」；手动删除归档包——只能等保留期到期，手动删等于毁证据；物理删除检测记录——只能走清理策略（有保护规则），不允许单条删；修改编码——已打印标签失效。

## 17. 数据归档与清理

检测记录不能无限堆在热存，也不能随便删——「当时为什么判 NG」要能追溯。

### 17.1 分层保留策略（默认值，可按产线覆盖）
| 数据 | 热存（SSD） | 归档（HDD/NAS） | 销毁 | 说明 |
|---|---|---|---|---|
| **NG 原图** | 30 天 | 12 个月 | 到期销毁 | 追溯价值最高，保留最久 |
| **OK 原图** | 7 天 | 不归档 | 7 天后删原图 | 只留缩略图 + 元数据 |
| 缩略图 + 元数据（分数/判定/模型版本） | 永久 | — | — | 体积小，支撑统计与追溯 |
| 进入数据集/验收集的样本 | 永久 | 模型退役后归档 | 模型删除后 1 年 | 训练证据 |
| 归档包 | — | 12 个月 | 到期销毁 | 每包含 manifest + 校验和 |

**为什么要区分 OK/NG**：OK 图占 90%+ 且几乎不会被回看；NG 图是争议、复检、再训练的证据。一刀切 30 天要么占爆磁盘，要么把证据删了。

### 17.2 保护规则与归档包

满足任一条即跳过清理：① 被 `dataset_item` / `pool_item` / `feedback` 引用；② 被**法务锁定**（客户投诉、质量事故、索赔）；③ 处于安全期（最近 3 天）；④ 属于当前 active 模型的**冻结验收集**；⑤ 人工标记「保留」。清理任务先算「可删集合」，再减去受保护集合；**受保护的一律跳过并计入报表**，不做「强制删除」开关。

```
archive/2026-11/AR-20261101-M-BR-01-b9f2.zip
  ├─ manifest.csv     id, 原路径, 产品, 模型版本, 分数, 判定, 时间, sha256
  ├─ images/…
  └─ checksums.sha256
```

打包后**校验回读**（核对 sha256），校验失败整个包判为无效并告警；数据库只改 `inference_result.archived_at / archive_id`，元数据始终可查；恢复 = 从包解出 → 回热存 → 标记 `restored_at`，**不重建数据库行**。

### 17.3 清理流程（必须二次确认）
```
预览 → 显示「将删除 N 条 / M GB，受保护跳过 K 条」
   → 二次确认（输入要删除的条数，防止手滑）
   → 分批执行（500/批），每批写审计
   → 生成清理报表（删除量、跳过量、剩余容量）
```

**磁盘水位联动**：>80% 告警；>90% 自动按策略归档 + 清理**无保护**数据，并记录「因水位触发」。

## 18. 抽样参数可配置化

每条线的产能与人力不同，抽选时间、总量、人工预算按线/按模型配置，不写死。

### 18.1 配置项（全局默认 + 按模型覆盖）
| 配置项 | 含义 | 默认 | 约束 |
|---|---|---|---|
| `run_at` | 每日抽选时间（HH:MM） | `02:00` | 合法时间；避开生产高峰 |
| `daily_cap` | 每日抽样总量上限 | 80 | ≤ 人工预算可处理量 + 自动入库量 |
| `ratio_pct` | 按昨日检测量的百分比抽样 | 0（不限） | 0~100；与 `daily_cap` 同时生效，先比例后封顶 |
| `allocation` | 配额分配方式 | `by_volume`（按昨日检测量） | `by_volume` \| `even` |
| `budget_min` | 人工复核时间预算 | 10 分钟 | 用于反推人工上限（按 6 s/张） |
| `caps.low` | 低置信送人工上限 | 40 | ≤ `budget_min × 60 / 6` |
| `caps.high_ok` | 高置信 OK 自动入库上限 | 20 | — |
| `caps.high_ng` | 高置信 NG 入池上限 | 10 | — |
| `caps.random` | 随机对照上限 | 10 | 用于偏差监控 |
| `low_range` | 低置信分数区间 | `[0.35, 0.65]` | 与高置信区间不得重叠 |
| `high_ok_max` | 高置信 OK 阈值 | `0.20` | < `low_range[0]` |
| `high_ng_min` | 高置信 NG 阈值 | `0.90` | > `low_range[1]` |

**按模型覆盖**：`daily_cap` 与 `caps.low` 可按模型单独设置，未设置则继承全局。

### 18.2 校验规则与生效

保存时校验拦截：① 时间格式合法；② `Σ caps ≤ daily_cap`；③ `caps.low ≤ floor(budget_min × 60 / 6)`（不能让配置超出人能判完的量）；④ `high_ok_max < low_range[0] ≤ low_range[1] < high_ng_min`（区间不重叠、不留空档）；⑤ `ratio_pct > 0` 时 `daily_cap` 仍作为硬上限（防止比例在小批量日抽太多）。保存后**次日生效**（避免当天跑到一半改配置导致前后不一致），页面明确提示生效时间；提供「立即执行一次」按钮（手动触发，用于调试）；每次变更写审计：谁、改了哪项、旧值 → 新值。

## 19. 页面职责划分：抽样独立，系统页只做系统

### 19.1 拆分原则
| 页面 | 只管 | 不管 |
|---|---|---|
| **抽样配置**（新） | 抽选时间、总量、比例、分配方式、分层上限与区间、按模型覆盖、变更历史 | 硬件、路径、服务状态 |
| **系统**（收窄） | **系统资源**（GPU/内存/磁盘）、**存放路径**、服务与自愈、运行环境、接入凭据 | 业务策略、抽样参数 |

判断标准：**改这个配置会不会影响「怎么判/抽什么」**——会，就是业务页；只影响「跑在哪、存哪里」，才在系统页。

### 19.2 系统页包含的内容

① **资源**：GPU 型号/显存/利用率/温度、内存占用、磁盘总占用；② **服务**：`AIP-Web`、`AIP-Worker` 的运行状态、PID、内存、运行时长、最近重启原因；③ **存放路径**（可编辑，改动需重启服务）：

| 用途 | 默认路径 | 可改 |
|---|---|---|
| 原图与缩略图 | `C:\AIP\data` | ✅ |
| 模型 bundle | `C:\AIP\artifacts` | ✅ |
| 数据库 | `C:\AIP\db` | ❌（迁移走备份/恢复流程） |
| 日志 | `C:\AIP\logs` | ✅ |
| 归档库 | `D:\AIP-archive`（建议独立盘/NAS） | ✅ |
| 备份 | `D:\AIP-backup` | ✅ |

④ **运行环境**：Python / torch / 驱动版本 / anomalib 版本 / Windows 版本；⑤ **接入凭据**：产线 token（可轮换）。

**路径变更的安全约束**：只允许**绝对路径**，且目录必须已存在（不自动创建，防止打错字建出垃圾目录）；改路径时校验新路径可用空间 ≥ 当前已用 × 1.2；保存后**不立即切换**，提示「重启 AIP-Web 与 AIP-Worker 后生效」，并写审计；数据库路径不可在界面改（要做迁移，走「备份 → 改配置 → 恢复」流程）。

## 23. 术语表
| 术语 | 含义 |
|---|---|
| 模型（`model`） | 一个检测任务实体，有自己的训练数据集；版本在其内部递增 |
| 模型版本（`model_version`） | 模型内的一次训练产物，状态 candidate / active / retired |
| 编码绑定（`model_binding`） | 产品编码 → 模型实体，不指向版本；一个编码只绑一个模型 |
| 产品编码 | 现场助记符，不透明字符串，创建后不可改，是路由键 |
| 配置单（`preset`） | 一组产品编码；操作工一键加载把对应模型预热进显存，只影响预加载不影响路由 |
| 常驻池（`serving_model`） | 已加载进显存的模型集合；超上限按 LRU 淘汰不在配置单里的模型 |
| 冻结验收集 | 指纹锁定的评估集，训练启动前校验指纹，变了就拒绝 |
| 样本池（`pool_item`） | 抽样与现场反馈汇入的待确认样本 |
| bundle | 模型产物单位：metadata + onnx + ckpt，自包含、可回滚 |
| coreset | PatchCore 记忆库的下采样比例 |
| PSI | 分数分布漂移指标，>0.2 告警 |
| 冒烟集 | 每产品 3~5 张已知结果图，发布/加载前自动核对 |
| 归档包 | 带 manifest 与校验和的离线证据包 |
| 法务锁定 | 因投诉/事故/索赔而禁止自动删除的标记 |
