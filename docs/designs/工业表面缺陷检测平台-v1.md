# 工业表面缺陷检测平台（v1）

* **Author:** zhoubin
* **Status:** Proposed（14 周方案，2026-11-14 定）
* **Date:** 2026-11-14

--------------------------------------------------------------------------------

## Overview

现状是每个产品型号一套独立的视觉检测程序，装在操作站本地电脑上，靠人工调 ROI、调参数、看效果。新型号从拿到样品到上线要 2~3 周，时间主要耗在现场调程序；判错走人工复检；漏检后果严重，所以策略是宁可错杀；历史图片有留存但没有索引，只能靠人翻。

这份设计不把"换一代检测算法"当作起点。评审阶段七个独立视角的结论指向同一处：真正缺的是**判据**——它现在只存在于几个人的经验和本地目录里，既不可检索，也不可复用，更无法验证。

但必须同时承认一个前提：**现在没有任何可用的模型资产**。现有的是规则型视觉程序，不是训练出来的模型，也没有可迁移的权重。因此推理与训练服务是**必需交付**，不是"实验之后再决定要不要做"；已选 ROI 声明化 + 重叠切块；实验用于确定 tile 边长、重叠率与接缝抑制参数，不再决定"整图还是切块"。

所以 v1 的范围是两件并行的必需项：一是从零训出第一个可用模型并让它在一台站位上以 assist 模式跑起来；二是让判据可以被记录、检索、复用。前者是"能用"，后者是"能长期用"。

## The Problem

**换型成本的构成不是单一的。** 2~3 周里至少混了四段：取图工况（光源、镜头、工位）、判据协商（什么算缺陷、边界在哪）、参数试凑（阈值、区域、特征）、部署（装程序、改配置）。换一代模型只能吃掉"参数试凑"这一段，而且会把工况差异从训练期推迟到运行期——省下的调参工时，会变成现场解释工时。

**判据没有被记录。** 判错的图有留存，但要靠人翻；"这张为什么判 NG"依赖当事人记忆。技师不在现场时，这个问题没人能回答，于是只能打电话、去现场。换型时间的实际瓶颈在这里，不在算法。

**没有现成模型，必须冷启动。** 现有系统是规则程序，没有可复用的权重或特征库。第一个模型只能从样品与历史图里训出来，而历史图没有索引、没有标签。这意味着两件事：一是必须先解决"多少张正常品、多少张缺陷图才能训出一个可用的模型"，二是第一个模型上线前没有可对比的基线模型，只能以规则程序的表现作参照。

**全量中心化未必是需求。** 现在 2~3 个站位共用一台服务器的计划，算力上并不紧张（3 站位约 1 张/秒，GPU 占用不到 1%）。真正绕不开的是"配置怎么下发、数据怎么回收"这两条通道，而不是把推理放到中心。

**"宁可错杀"与"复检率下降"相互拉扯。** 错杀率高意味着每班上百次额外动作。只要 NG 出口比 OK 多一步，操作工就会把 NG 塞进 OK 箱或开回旧程序——这是漏检的真实来源，而且系统内的数字反而更好看。

## Goals

1. **从零产出第一个可用模型**：在没有可迁移权重的前提下，用样品与历史图训出一个模型，在至少一个产品编码上以 assist 模式运行（判但人定），漏检与过杀按 Acceptance Protocol 的抽检双盲口径度量（基线由旧系统用同一协议测得），不以"零上报"作为通过依据。这条是"能用"的最低证据。
2. **判例库可检索**：至少一个型号积累 30 条判例（可接受/不可接受各 15 条），每条含原分辨率裁剪图、一句话理由、裁决人与时间，且能按型号、编码、裁决人检索。v1 只做判例库，**不做判据结构化**（缺陷类型/可接受条件等字段留到 v1.1），因此"判据可复用"在 v1 内不承诺。
3. **漏检不增加（抽检双盲）**：以同一套抽检协议在旧系统上先测 2 周得到基线，assist 期间按周抽检；累计人判 NG ≥20 件方可判定，漏检率（系统判 OK 而人判 NG 的比例）不高于基线。样本不足时标"不可判定"，**不得用"零上报"代替**。
4. **复检负担可度量**：主指标"每千件复核分钟数"，在 assist 期与基线期用**同一计量方法**（固定计时人、起止点、样本量）实测；分母是同期待复核件数，不是总产量。
5. **低技能依赖（仅限模型与配置层面）**：换型对操作工是一个动作（≤1 次点击）；技术员只提供样品与可接受/不可接受判断，不接触阈值、学习率、coreset 等参数。光源、镜头、工位的调整不在此列——它们不在平台范围内。
6. **判定可追溯**：任何一张图都能回答"哪一版模型判的、送进去的是哪张图、分数多少、ROI 在哪"，且能按 result_id 反查原始整图（7 天内）。

## Non-Goals

- 多产线、细粒度 RBAC。
- 合规归档包与法务锁定（属客户合规需求，不在本轮）。
- 配置单 CRUD、容量预检（容量当前不是约束）。
- 统计大屏、掩膜标注、缺陷定级。
- 自动训练自动上线（首年只出候选，人点发布）。
- **换型时间下降的验证**：需要第二个编码才有度量对象，留到 v1.1；v1 只保证单编码能跑通。
- **active 切换**：v1 的终点是 assist（判但人定）；active 的自动放行留到 v1.1，届时需另一轮评审。
- **验收集扩样到 50 张**：v1 用 15 张且只做否决性检查；扩样与"召回不降"的统计判定留到 v1.1。
- **换倍率/换窗口复判**：因采用现场裁剪后上传，系统只具备"原图重看"能力，不具备"用另一种放大倍率重新判定"的能力。这条写进非目标，避免以后被当成缺陷。
- 站位承载 ROI 决策：ROI 由服务端随模型版本下发，站位只执行裁剪。

## 生产并存期（Coexistence）

新旧系统必须并存一段时间，否则 shadow 没有对照、切换没有退路。

**四个阶段**

1. **并行观察（shadow，v1 覆盖）**：旧程序照常判定，新系统只记录不判；能否进 assist 见「门槛状态表」G2（旧程序一致率只作诊断，不作门槛）。
   **标签来源**：旧程序输出只是"对照结论"，不是真值；真值只来自抽检双盲的子集（每周 300 件）。两者都记，不混为一谈。
2. **人机协作（assist）**：新系统判定但人定；面板同时显示旧程序结论作参考，冲突时以人判为准并记录冲突原因。
3. **切换（active，v1.1）**：旧程序转为只读对照，旧机保留 4 周冷备（断电，可随时开机）。
4. **停用（v1.1）**：连续 4 周 active 且抽检双盲达标，旧程序停机；旧机与旧程序目录保留 3 个月后归档。

**责任边界**

- 相机、镜头、光源、工位：设备方负责，平台不控制（见 Non-Goals）。
- 旧程序的启停与版本：产线负责，平台不接管。
- 冲突裁决：shadow 期不裁决、只记录；assist 期由操作工或质量员裁决，并记录理由。

**回退触发**：单周漏检见 G5，连续两周见 G6；另有两条并存期专属触发（站位健康度连续告警、旧程序停用后出现批量误判），均按 G6 处理。

**数据边界**

并存期内两套结论都入库，旧程序结论标记 `source=legacy`，便于事后比对；切换完成后旧结论保留只读，不参与训练与门槛计算。

## Acceptance Protocol（抽检双盲）

验收不依赖"操作工自愿上报"——那条通道在 NG 出口比 OK 多一步时必然被绕过。改为**每周固定抽检、人机盲判、签字冻结**。

**频率与样本**：每周固定一天执行；从当周产量按时间分层随机抽 300 件；NG 与灰区件**全数纳入**，若其数量已超过 300 件则以 NG/灰区为准，不足则用随机 OK 补足 300。随机种子由质量方生成并留档，业务方不得预先知道抽中哪些。

**盲判方式**：质量员只看件，不知道系统结论；另一个人导出系统结果。两侧独立记录后比对，任一方不得在比对前看到另一方。

**记录字段**：件号、时间、系统三态、人判（OK/NG/灰区）、判定人、时间戳、`model_version`、签字。

**指标**：漏检率（系统 OK 而人判 NG）、过杀率（系统 NG 而人判 OK）、灰区率、不一致率。分母取人判口径，不取系统口径。

**判定条件**：见「门槛状态表」G4；本协议只定义"怎么抽、怎么判、怎么记"，不重复门槛数值。

**失败处置**：单周出现漏检见 G5，连续两周见 G6。v1 没有 `active`，"回滚到上一个 active"不适用。

**样本不足时的替代路径**：见「门槛状态表」G7。**没有这条路径，整个验收会卡在"永远凑不够 20 件"上。**

**基线同源**：旧系统用同一协议测 2 周，作为 Gate 0 的基线数据。这样"漏检不增加""每千件复核分钟数下降"两个目标才与基线同量纲。

## 门槛状态表（唯一来源）

所有门槛只在本表定义，正文其他位置只引用编号，不再重写条件。

| # | 门槛 | 状态迁移 | 通过条件 | 未通过处置 |
|---|---|---|---|---|
| G1 | 候选 → shadow | candidate → shadow | 冒烟集 3~5 张、与人工核对一致率 100% | 停在候选 |
| G2 | shadow → assist | shadow → assist | ≥500 张，且在抽检双盲子集上与人判一致率 ≥90% | 退回分析，不推进 |
| G3 | assist 维持 | assist 保持 | 每周抽检漏检 = 0 | 触发 G5 |
| G4 | 验收结项 | assist 结项 | 连续 4 周、累计人判 NG ≥20、漏检 0、三方签字 | 走 G7 或延长 |
| G5 | 单周出现漏检 | assist → shadow | —— | 24h 复盘、48h 处置（重标定/换版本/补样本） |
| G6 | 连续两周漏检 | assist → 停用 | —— | 回旧程序，修复后重走 G2 |
| G7 | 样本不足 | assist 延长 | 抽检提到 600 件/周并延至 8 周；仍 <20 件 | 质量与产线书面同意，低置信结项并注明 |
| G8 | 回滚传播 | 任意 → 新版本 | 全站位 `config_rev` 回执一致 | 已回执先开放，未回执标 manual 并告警，上限 120s |
| G9 | 过杀率门槛 | assist 期间持续 | 过杀率 ≤ max(在用版本 + 2pp, 5%) | 不结项，继续观察并复盘 |

**旧程序一致率（≥90%）不在门槛之列**，只作诊断：旧程序不是真值，把它当门槛等于把旧系统的"宁可错杀"写进发布条件。

## Open Questions

* **Q1（阻断）**：切块参数如何定？已选"ROI 声明化 + 重叠切块"，但 tile 边长、重叠率、聚合规则（max 分数 / argmax 定位）与接缝假阳性的抑制方式需要实验确定。维度：tile 边长（256/384/512）× 重叠率（0/25%/50%）× 聚合规则，指标为小缺陷召回与单图耗时。
* **Q2（已决定）**：部署形态取中心推理（A），见 Technical Plan。「统一分发 + 收数据」作为断网场景备选保留，不再作为开放问题。
* **Q3（影响预算）**：5090 是否必要？当前测算 GPU 占用不足 1%，训练可放到办公机；若确认，服务端可降规格，预算转向光源与相机。
* **Q4（阻断验收）**：基线数据能否拿到？旧系统记录是否可导出、由谁签字冻结。
* **Q5（影响正确性）**：站位裁剪的入口守门阈值如何定？尺寸、亮度、对比度、边缘完整性的合格范围需要一批真实裁片统计得出。
* **Q6（部署前置）**：目标机驱动是否 ≥580？若低于此版本，cu130 轮子不可用，需准备 cu118 分支并重做离线包。此条不确认不得开工。

## Critical User Journeys

### CUJ 1：换型

* **Given**：站位在线，服务端已为该产品编码绑定了模型版本与 ROI 配置，操作工在工位面板前。
* **When**：扫描产品编码，站位先校验是否在**本班白名单**（`configs/shift_whitelist.yaml`，一行一组，不建表）；不在则提示"本编码不在本班范围"并给"跳过/联系技师"。通过后 `GET /station/config?code=...` 拿到 `{model_version, roi_rev, roi_rect, preprocessing}` 并应用；服务端确保该 `model_version` 已常驻，未常驻则单飞加载（站位不加载模型，也不做预热）。
* **Then**：面板显示"就绪，可开工"，耗时 ≤ 5 s（首次含服务端常驻加载）；失败时显示可点动作（重试 / 联系技师 / 转人工全检），不显示错误码。

### CUJ 2：推图判级

* **Given**：站位已换型、模型已就绪，产品在工位。
* **When**：拍照 → 按 `roi_rect` 裁剪 → 上传裁片与元数据（code、station_id、ts、roi_rev、idempotency_key）→ 服务端入口守门 → 批推理。
* **Then**：返回 OK / 灰区 / NG 三态之一，附分数与命中区域；三态在面板上的操作路径长度一致（NG 不比 OK 多一步）；灰区给出第二证据（邻块一致性、同批次分布；因采用现场裁剪且放弃换倍率复判，不提供"重新裁剪再看"这条路）。

### CUJ 3：判错上报

* **Given**：操作工认为判定不对，面板显示当前 result_id。
* **When**：点"判错了"，选择"其实该判 NG / 其实该判 OK"，可选一句话原因。
* **Then**：3 秒内完成，写入 feedback；该图进入复核队列；若判"其实该判 NG"，服务端立即向站位拉取原图转存。

### CUJ 4：判据入台账

* **Given**：技术员在中心看到一条争议图或新采样本。
* **When**：在页面上点"可接受 / 不可接受"，填一句话理由，确认裁决人。
* **Then**：生成判例库条目（裁片 + 理由 + 裁决人 + 时间），可按型号、编码、裁决人检索；该条目可直接进入下一次训练的数据集。

### CUJ 5：新型号上线

* **Given**：拿到新样品与"可接受/不可接受"的判断标准，技术员不接触任何算法参数。
* **When**：上传样品 → 系统按型号切分训练/验收集 → 夜间训练出候选 → 冒烟（抽 3~5 张已知判例核对）→ 人工点发布。
* **Then**：新版本先以 `shadow`（只记录不判）运行，再 `assist`（判但人定）；v1 到 `assist` 为止，`active` 属 v1.1。任一步不满足门槛即停在候选，不自动上线。

### CUJ 6：工位复核（操作工版）

* **Given**：面板底部显示"待确认 N 件"（本工位、`label ∈ {ng, gray}` 且 `confirmed_at` 为空）。
* **When**：点开队列 → 逐件大图展示（分数、命中区域、送检图）→ **默认选中系统结论** → 接受是一次点击；改判才需选一条预设理由（划痕/脏污/压伤/误报/其他）。
* **Then**：写 `confirmed_by` / `confirmed_at` / `confirm_note`；待确认数减一；改判件同时进判例库候选（来源标记 `result`）。队列只显示本工位，不做筛选、不分页、不打字。

## Technical Plan (Architecture)

### 运行平台（Windows 11）

- **目标平台**：Windows 11 x64 **专业版**（生产机）；开发机为家庭版，已验证代码可在两者上运行。
- **服务托管**：NSSM 注册两个 Windows 服务（`AIP-Web`、`AIP-Worker`）；走 SCM，不依赖专业版特性。
- **专业版可用但不强依赖**：RDP 主机（远程维护）、BitLocker（可选，磁盘加密）、组策略（锁定 Windows 更新时段）。这三项写进部署手册，但方案本身在家庭版也能跑。
- **明确不用**：Hyper-V（不需要虚拟机）、Docker/WSL（已否决）。
- **路径与编码**：所有路径用 `pathlib`，不拼反斜杠字面量；控制台统一 `PYTHONUTF8=1`，日志强制 UTF-8（GBK 控制台会炸 emoji）。
- **离线**：依赖离线 wheelhouse + 内置权重；`pip install --no-index --find-links` 是唯一安装方式。
- **开发机与目标机同平台**：本机 Windows 11 家庭版已验证可跑（Python 3.13 + SQLite WAL）；目标机建议同版本或更高。

| **Station Agent**（站位，薄） | 拉配置、拍照、按 `roi_rect` 裁剪、上传裁片、本地环形缓存原图 7 天、接受服务端"按需拉原图"请求 | 不判定、不存判据、不改 ROI、不装模型 |

### 关键机制

**三态出口。** OK / 灰区 / NG。人因设计的关键不是"三态路径等长"，而是**让危险方向变贵**：assist 期 NG 与灰区必须人工确认：确认框默认选中系统结论，接受是一次点击；改判为 OK 需额外填一句原因。这样危险方向（把 NG 改成 OK）更贵，而接受系统结论只需一次点击。灰区与 OK/NG 同级，点了就出第二证据（邻块一致性、同批次分布），人只处理互相矛盾的残差。

**三态判定。** 每个模型版本带两个阈值，存库并与 `model_version` 绑定（不写进 bundle）。**这是对仓库现有"阈值随 bundle 走"不变式的有意修改**：bundle 只装权重与预处理，阈值、ROI、切块参数由库管理，好处是可以在不重新导出权重的前提下重标定；代价是 `bundle.py` 与 README 的相关描述必须同步更新，否则两处说法打架。`th_lo` 用过杀目标在**全部正常品**上估计（正常品应 ≥100 张；不足时标注"置信不足"），取使过杀 ≤5% 的分数点；`th_hi` 用缺陷验收集估计，取使召回 ≥0.95 的分数点（15 张时分辨率 6.7pp，必须标注）。判级：`score < th_lo` 为 OK，`th_lo ≤ score < th_hi` 为灰区，`score ≥ th_hi` 为 NG。

若 `th_lo > th_hi`（两类分布重叠、灰带为空），**不判"不可发布"**：按"宁可错杀"取召回优先，令 `th_hi` 为唯一阈值、灰区为空，并记录该版本为**高过杀模式**，过杀率单独统计并触发复盘。理由是：要求 `th_hi > th_lo` 等于要求两类分布在 5% 尾部完全分离，而 8 张正常品估不出 5% 分位——按旧写法，v1 几乎必然没有交付物。

灰区**不计入过杀率**，单独统计灰区率（初值上限 10%）；切块参数、重叠率或预处理变更必须重新标定，旧阈值作废。

**重叠切块。** 站位裁出的 ROI 在服务端按固定 tile 边长与重叠率切开，逐块推理后聚合：分数取各块最大值，位置取最高分块的 argmax。重叠的目的是避免缺陷正好落在切缝上；代价是推理次数与记忆库按块数增长，接缝处可能出现假阳性，聚合时要加邻块一致性检查（相邻三块中至少两块同时报警才计入）。

**训练窗口。** 训练只在约定夜间窗口（默认 01:00–05:00）执行，窗口内推理暂停，站位转人工全检并在面板明示。若当夜有生产排班，训练顺延到下一个空窗，不抢占推理。PatchCore 的 `Engine.fit` 是单次调用、中途无法安全中断，因此"边训边推、延迟超阈值就暂停"不可实现——只能做任务边界的前置检查（开始前看排队与延迟），不能中途让路。

**推理后端。** 生产侧只装 onnxruntime，不装 torch：训练结束时导出 ONNX（`external_data=False`，单文件），并在冻结验收集上比对导出前后的分数，最大偏差须 < 1e-3，否则不允许发布。收益是生产镜像体积与启动时间下降；代价是排查链路多一环——导出本身可能引入偏差，因此每次导出都要跑一次一致性校验。

**灰度状态机。** 三态推进与每态条件见「门槛状态表」G1–G6，此处只写行为、不重复数值：`shadow` 只记录不判；`assist` 下 **NG 与灰区必须人工确认后才成为最终判定，OK 直接放行但受每周抽检监督**；`active` 属 v1.1（NG 也不再逐件确认，只做异常升级）。不允许跳级，任一步未满足即停留在当前态。

**回滚传播。** 回滚不是"改一个指针"：新模型必须与它绑定的 `roi_rev` 成对生效，否则会出现"新模型 + 旧窗口"的错判。流程固定为：全局暂停推理 → 发布 `model_version` 与配套 `roi_rev` → 等站位心跳回执 `config_rev` 一致 → 重新开放。站位心跳周期 10 s；等待上限 120 s，超时则**已回执的站位先开放，未回执的标记为 manual 并告警**，不因单个掉线站位阻塞全线。暂停期间站位转人工全检并在面板明示，不允许放行。夜间训练窗口内触发回滚时，先在任务边界终止训练，再执行回滚，两者不重叠。3 站位下的目标窗口 ≤ 2 分钟（从点回滚到重新开放，取 5 次中位数）。

**编码生命周期（模型是能力，编码是入口）。** 一个模型可以被多个产品编码绑定——模型提供"会不会判"，编码提供"操作工选哪个"。编码多了要有收敛机制，否则现场选择器会越来越长：

- **启用**：可推图、出现在选择器里。
- **停用**（`active=0`）：不可推图（站位返回 410），但仍在列表里，可随时启用；历史与追溯保留。
- **归档**（`archived_at` 非空）：从默认列表与操作工选择器消失，只能在"显示已归档"里看到；**仍有活跃绑定时禁止归档**，避免现场扫到一个没有模型的入口。恢复是一键操作。

操作工的选择器只列"启用且未归档"的编码；归档不删数据，任何历史判定仍可按编码查出。

**入口守门。** 服务端收到裁片先做四项校验（尺寸、亮度、对比度、边缘完整性），不合格不入队，直接返回可点动作（"请检查定位"），并计入站位健康度；连续 N 次不合格告警到技师。阈值由首批真实裁片统计得出（Q5）。

**单飞加载 + 常驻池。** 模型按 `(model_version, roi_rev)` 常驻；未命中时只允许一个加载请求并发，其余等待同一结果；容量满时按 LRU 淘汰不在当前配置里的模型。

**配置下发。** 站位主动拉取，带本地缓存与 `roi_rev` 回执；服务端记录每个站位最后生效的 `config_rev`，页面可看到"哪些站位还没生效"。站位缓存的版本与模型版本必须成对，禁止交叉组合。

**证据链。** 每条 result 存：裁片路径、ROI 矩形、原图尺寸、送检图（降采样后）、分数、`model_version`、`job_id`、耗时。原始整图只存站位本地 7 天；NG、复核、争议三类图由服务端立即拉取转存，不依赖 7 天窗口。

**工位复核队列。** 待确认件由查询得出（`label in ('ng','gray') and confirmed_at is null and station_id = ?`），不另建队列表。队列按时间倒序、只显示本工位、上限 50 件；超过则提示"积压 N 件"但不阻塞生产。技术员在管理页可看全量并代确认，代确认也写 `confirmed_by`，事后可追责。

**本班白名单。** 只放在 `configs/shift_whitelist.yaml`，一行一组编码，不建表、不做界面；站位扫码时校验，不在名单即提示并给动作。改白名单需重启 Worker 或热加载配置，属低频操作。**这不是预热配置，不触发加载**——加载永远按需（单飞）。

**失败语义。** 服务不可用时，站位进入"人工全检"模式并在面板明示，不产出自动判定，不允许"临时放行"。停机期间站位缓存不丢图，恢复后补传；补传的图不入判定队列，标记为 `missed` 进池供人工复核与训练，避免用过期模型判旧图。

**写入模型。** SQLite 自身提供跨进程写锁，不引入进程内锁：所有写事务短于 100 ms，连接统一 `busy_timeout=5000`，禁止长事务。API 只写入队行与体征类小记录，Worker 只写结果与状态，Train Worker 只写训练任务与指标，三者靠数据库锁串行化。

**冷启动。** 没有可迁移权重，第一个模型只能从零训练：正常品达到最低张数（初值 100，`th_lo` 需在全部正常品上估计）与缺陷图达到下限（初值 30，因验收集取 50%，需 15 张入验收集）才允许训练，样本不足时明确拒绝并回答"还差多少张、缺哪一类"。切分沿用一次性冻结（正常品 20% + 缺陷图 50% 进验收集，指纹锁死）。由于没有在用模型可对比，第一个候选的门槛以**同编码规则程序的历史表现**为参照，并要求冒烟集 3~5 张人工核对通过才允许 assist。此后每一版都只与同模型的上一个 active 版本比较，不跨模型平均。\n\n**验收集的效力限制。** 冻结验收集缺陷图仅 15 张，1 张差异即 6.7 个百分点，因此它只用于趋势观察与否决性检查（出现已知漏检即阻断），不用作"召回提升/不降"的统计判定。要获得可判定的召回比较，需扩到 50 张以上；在扩样之前，发布门槛以冒烟集一致率与 assist 期人工反馈为准。

## Alternatives Considered

### Alternative A：继续用传统视觉工具，只加强管理（统一目录、统一命名、统一升级）

* **Pros**：不引入新算法风险；现场人员熟悉；短期零学习成本。
* **Cons**：换型仍需人调 ROI 与参数；判据仍不可检索；升级仍要逐台处理。
* **Reason for Rejection**：Rejected by author —— 人工依赖不降，换型时间不变，等于没解决"效率与经验压在人工身上"这个主诉。

### Alternative B：维持每站位本地部署，只做数据回收

* **Pros**：断网可继续；延迟最低；无需中心算力。
* **Cons**：站位需要 GPU 或高性能 CPU，2~3 套成本高于一台服务器；版本一致性靠人；判据仍分散。
* **Reason for Rejection**：Rejected by author —— 成本与一致性都不划算，但它作为**迁移期冷备形态**保留。

### Alternative C：全量中心服务，按原方案 12 周交付

* **Pros**：功能一次到位，含归档、配置单、权限、大屏。
* **Cons**：评审判定 78 人日对 57.5 人日、周次超载 1.6~2.8 倍；45 条行动项中 14 条阻断；12 条验收仅 2 条可直接测。
* **Reason for Rejection**：Rejected by author —— 排期不成立，且范围里混入了合规客户需求（归档）与多线将来（RBAC），不是单线试点该付的代价。

### Alternative D：只做"统一分发 + 统一收数据"，推理留在站位

* **Pros**：断网可用；中心不被推理绑定；自研约 3k 行可覆盖。
* **Cons**：站位需运行时与算力；版本一致性最难；远程诊断最弱。
* **Reason for Rejection**：Rejected by author —— 当前内网同交换机、单图仅几十 KB，网络不是瓶颈；而站位运行时与一致性带来的长期运维成本高于集中推理。若将来出现"必须断网运行"的硬约束，此方案应重新评估。

### Alternative E：ROI 在服务端裁剪，站位只上传原图

* **Pros**：证据完整，可换倍率复判；改 ROI 立即生效；站位零配置。
* **Cons**：带宽与解码压力上移；服务端要存原图（约 81 GB/30 天，3 站位）。
* **Reason for Rejection**：Rejected by author —— 站位本来就在取图与预处理，裁剪不增加新环节；服务端只处理小图，单卡可带更多型号。代价以"7 天本地原图 + NG 立即拉取 + 入口守门"三条补偿承接，并明确放弃换倍率复判。

### Alternative F：配置用服务端推送或共享文件夹

* **Pros**：推送生效最快、能实时收状态；共享盘实现最省。
* **Cons**：推送需要常驻长连接，网络抖动即失去控制面；共享盘无版本回执，权限与并发写易错。
* **Reason for Rejection**：Rejected by author —— 拉取模式允许站位离线用缓存继续跑，且服务端能记录每个站位的 `config_rev` 回执，满足"能看到哪些站位没生效"的运维需求。

### Alternative G：PostgreSQL 或"台账文本化"

* **Pros**：PG 迁移工具成熟、并发强；台账文本化可 diff、可评审、可回滚。
* **Cons**：PG 多一个要装要备要升级的服务；台账文本化存在"文件与库不一致"的同步问题。
* **Reason for Rejection**：Rejected by author —— 单机 2~3 站位的写入量用 SQLite（WAL + 单写者）足够；台账需要页面内编辑与检索，放进库比放文件更直接，审计靠 `audit_log` 与版本字段，不靠 git diff。
